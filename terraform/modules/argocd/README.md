# argocd

Installs ArgoCD itself and then hands off nearly everything else to it: the sample app, the observability stack (Prometheus/Grafana/Alertmanager), Loki, and Grafana Alloy are all defined here as ArgoCD `Application` resources rather than installed directly by Terraform. This module also owns three namespaces (`argocd`, `railhead`, `monitoring`) and a couple of Secrets that the GitOps-managed workloads need but shouldn't generate for themselves.

**ArgoCD itself** (`helm_release.argocd`, chart `argo-cd`, version pinned via `argocd_chart_version`). Its Helm values register a custom Lua health check for the Prometheus Operator's `Prometheus` CRD — ArgoCD's generic default health check looks for a `type: Ready` status condition, but that CRD reports `Available`/`Reconciled` instead, so without this customization a fully healthy Prometheus would perpetually show as "Progressing" in ArgoCD.

**Repo access.** `kubernetes_secret_v1.repo_credentials`, labeled `argocd.argoproj.io/secret-type: repository`, is how ArgoCD auto-discovers credentials to clone the private `railhead` repo — no separate `argocd repo add` step needed. This is a distinct identity/auth path from the GitHub Actions OIDC federation built in the `iam` module: that's scoped to GitHub Actions CI runs specifically, and doesn't help a long-lived in-cluster controller that polls git on its own.

**The `railhead` Application.** A git-repo-source Application (`repoURL` + `path` + `targetRevision: main`) pointed at `kubernetes/helm-charts/railhead-app`, with `syncPolicy.automated.prune`/`selfHeal` both on. This is the actual GitOps definition — instead of a human running `helm install`, ArgoCD watches the path in git and continuously reconciles the cluster to match it.

**Postgres auth stability.** The sample app's Postgres password is generated once via `random_password` and stored in a Terraform-owned `kubernetes_secret_v1` (`railhead-postgresql-auth`), referenced by the Helm chart's `postgresql.auth.existingSecret` rather than letting the Bitnami chart generate its own. The chart's own password-generation logic relies on Helm release history (via a `lookup()` call) to avoid regenerating the password on every upgrade — but ArgoCD has no such history; it re-renders the chart from scratch on every sync. Without this fix, a resync can silently regenerate and overwrite the password out from under an already-initialized Postgres pod, which only ever recognizes whatever password was present at its own first boot.

**The `observability` Application.** A Helm-chart-repo-source Application (chart `kube-prometheus-stack` + `targetRevision` as the chart version, not a git path) rather than the git-repo-source flavor `railhead` uses — ArgoCD supports both. Notable choices inside its `valuesObject`:
- `crds.enabled = false` — this chart's own CRDs are large enough to hit Kubernetes' 256KiB total-annotation-size limit under client-side apply, and `syncOptions: ["ServerSideApply=true"]` (the documented fix) didn't resolve it in practice here even after a forced hard refresh. The CRDs were bootstrapped once, manually, outside GitOps entirely (`kubectl apply --server-side` against the chart's own `crds/` directory) — see the gotcha below.
- `kubeControllerManager`/`kubeScheduler`/`kubeEtcd`/`kubeProxy` all disabled — AWS manages these control-plane components on EKS and doesn't expose their metrics endpoints, so leaving them enabled would just create permanently-"down" scrape targets with nothing actionable about them.
- `prometheus.additionalServiceMonitors` scrapes `railhead-api`'s `/metrics` endpoint. This key is a *sibling* of `prometheusSpec`, not nested inside it — misplacing it one level too deep is a silent no-op in Helm, not an error.
- `alertmanager` is fully configured here: enabled, with the webhook URL for Slack mounted via a separate `kubernetes_secret_v1` (`alertmanager_slack_webhook`) and referenced with `api_url_file` rather than `api_url` — the raw URL would otherwise sit in plaintext in this Application's own `spec.source.helm.valuesObject`, readable via `kubectl get application observability -o yaml` by anyone with basic read access to Applications. Routing sends `severity=critical` and `severity=warning` to one shared Slack receiver (color/emoji distinguish them at notification time via Alertmanager's own Go templates), everything else (e.g. the chart's built-in `Watchdog` heartbeat) to a `null` receiver.
- `additionalPrometheusRulesMap` defines two SLOs (99% availability, 95% of requests under 300ms), each with the Google SRE Workbook's multi-window multi-burn-rate pattern — a fast/critical rule and a slow/warning rule per SLO, four alerting rules total. Defined here via Helm values rather than as a Terraform-managed `PrometheusRule` CRD instance, for the same CRD-ordering reason `crds.enabled = false` exists above (see gotcha below).
- `grafana.persistence` is enabled (a second real use of the EBS CSI driver besides Postgres), but persistence alone isn't the durable fix for dashboards — a PVC can still get wiped by an incident. The actual fix is the two `kubernetes_config_map_v1` resources at the bottom of the file (`railhead_api_metrics_dashboard`, `railhead_cluster_health_dashboard`), which load dashboard JSON from `kubernetes/observability/dashboards/` via `file()` and label the ConfigMap `grafana_dashboard: "1"` directly — deliberately *not* using the chart's own `grafana.dashboards` values key, since that key's own template labels its generated ConfigMap `dashboard-provider: default`, not the `grafana_dashboard: "1"` label the sidecar actually watches for, so anything loaded through it is silently never picked up.

**The `loki` Application.** Loki in `SingleBinary` mode (all components in one process, the right tradeoff for this cluster's actual log volume) rather than the chart's own `SimpleScalable` default — which requires explicitly zeroing `read`/`write`/`backend` replicas, since the chart doesn't do this automatically and a combined-mode apply otherwise fails validation. S3-backed chunk storage using the bucket/IRSA role built in the `iam`/`eks` modules. `commonConfig.replication_factor = 1` — the chart's default of 3 assumes a multi-replica ring, which a single `singleBinary` pod can never satisfy. `schemaConfig` (TSDB index type) is a required field with no default. Retention is 168h (7 days).

**The `alloy` Application.** Deployed separately from Loki — the Loki chart has no Alloy dependency at all (its `Chart.yaml` only depends on `minio`, `grafana-agent-operator`, and `rollout-operator`). Alloy runs as a DaemonSet, using `loki.source.kubernetes` (Kubernetes-API-based log tailing) rather than the traditional hostPath-mount approach, and needs an explicit `rbac.clusterRules` block — this chart ships an *empty* ClusterRole by default, so without supplying rules, Alloy's pods would run but silently collect nothing.

**The `loki_datasource` ConfigMap.** Reuses the exact same Grafana sidecar mechanism as the dashboard ConfigMaps above — same chart, same sidecar, just watching `grafana_datasource` instead of `grafana_dashboard`.

## Known gotchas

- **Two-pass apply is required on a from-scratch deploy.** `kubernetes_manifest` validates its manifest's schema against the *live* cluster at plan time. On a fresh cluster, the `Application` CRD doesn't exist until `helm_release.argocd` has actually applied — so a single `terraform apply` that includes both `helm_release.argocd` and any `kubernetes_manifest.*_application` resource fails, even with `depends_on` set correctly (`depends_on` only controls apply *order*, not plan-time schema validation). Fix: first apply targeting just `helm_release.argocd` (and the namespaces it needs), then a normal full apply once the `Application` CRD exists.
- **kube-prometheus-stack's own CRDs need a manual one-time bootstrap.** Since `crds.enabled = false`, this module never installs the `Prometheus`/`Alertmanager`/`ServiceMonitor`/`PrometheusRule` CRDs. On a genuinely fresh cluster, these must be applied once by hand — `kubectl apply --server-side` against the chart's own `crds/` subdirectory — before the `observability` Application can sync successfully. This isn't captured in code anywhere; it's an operational step to remember when rebuilding from scratch.
- **The Prometheus health-check Lua script and any other `argocd-cm` change may need a controller restart to take effect** — the `argocd-application-controller` can cache CRD/config discovery at startup and not notice a change until restarted.
- **Postgres password stability** (see above) is a real, previously-hit failure mode, not a hypothetical — worth remembering if the `railhead` Application's chart values or its Postgres subchart version ever change.

**Inputs:** `github_repo_url` (default `https://github.com/Levi-TenshiOps/railhead`), `argocd_chart_version` (default `10.1.3`), `github_token` (required, sensitive), `slack_webhook_url` (required, sensitive), `kube_prometheus_stack_chart_version` (default `87.17.0`), `loki_chart_version` (default `7.1.0`), `alloy_chart_version` (default `1.10.1`), `loki_bucket_name` (required, from the `iam` module), `loki_irsa_role_arn` (required, from the `eks` module).

**Outputs:** `argocd_namespace`, `railhead_namespace`.
